---
title: "Agent Skills"
description: "Define reusable behavior via SKILL.md definitions"
---

Agent skills let OpenCode discover reusable instructions from your repo or home directory.
Skills are loaded on-demand via the native `skill` tool—agents see available skills and can load the full content when needed.

---

## Place files

OpenCode supports two file layouts for skills:

- **Nested**: one folder per skill with a `SKILL.md` inside — `.opencode/skills/<name>/SKILL.md`
- **Flat**: a single `.md` file whose name becomes the skill name — `.opencode/skills/<name>.md`

Both layouts are discoverable under `.opencode/skill/` and `.opencode/skills/`.
Claude- and agent-compatible directories (`.claude/`, `.agents/`) only support the nested `SKILL.md` layout.

Full list of search locations:

- Project config (nested or flat): `.opencode/skills/<name>/SKILL.md` or `.opencode/skills/<name>.md`
- Global config (nested or flat): `~/.config/opencode/skills/<name>/SKILL.md` or `~/.config/opencode/skills/<name>.md`
- Project Claude-compatible: `.claude/skills/<name>/SKILL.md`
- Global Claude-compatible: `~/.claude/skills/<name>/SKILL.md`
- Project agent-compatible: `.agents/skills/<name>/SKILL.md`
- Global agent-compatible: `~/.agents/skills/<name>/SKILL.md`

---

## Understand discovery

For project-local paths, OpenCode walks up from your current working directory until it reaches the git worktree.
It loads any matching `skills/*/SKILL.md` (and `skills/*.md` under `.opencode/`) along the way, plus any matching `.claude/skills/*/SKILL.md` or `.agents/skills/*/SKILL.md`.

Global definitions are also loaded from `~/.config/opencode/skills/`, `~/.claude/skills/`, and `~/.agents/skills/` using the same patterns.

---

## Write frontmatter

Each skill file must start with YAML frontmatter.
Only these fields are recognized:

- `name` (required for flat `.md` files; for nested `SKILL.md` it falls back to the parent directory name when omitted)
- `description` (optional, but strongly recommended so the agent can pick the right skill)

Unknown frontmatter fields are ignored.

---

## Validate names

Skill `name` should follow these conventions so it stays portable and discoverable:

- Be 1–64 characters
- Be lowercase alphanumeric with single hyphen separators
- Not start or end with `-`
- Not contain consecutive `--`

Equivalent regex:

```text
^[a-z0-9]+(-[a-z0-9]+)*$
```

For nested `SKILL.md` files, the `name` should match the parent directory name. For flat `.md` files, the `name` defaults to the filename without the `.md` extension when not set in frontmatter.

---

## Follow length rules

Keep `description` under 1024 characters.
Make it specific enough for the agent to choose correctly — a vague description like "helps with code" leads to wrong skill selection.

---

## Use an example

Create `.opencode/skills/git-release/SKILL.md` like this:

```markdown
---
name: git-release
description: Create consistent releases and changelogs
---

## What I do

- Draft release notes from merged PRs
- Propose a version bump
- Provide a copy-pasteable `gh release create` command

## When to use me

Use this when you are preparing a tagged release.
Ask clarifying questions if the target versioning scheme is unclear.
```

Or use the flat layout at `.opencode/skills/git-release.md` with identical frontmatter.

## Recognize tool description

OpenCode lists available skills in the `skill` tool description.
Each entry includes the skill name and description:

```xml
<available_skills>
  <skill>
    <name>git-release</name>
    <description>Create consistent releases and changelogs</description>
  </skill>
</available_skills>
```

The agent loads a skill by calling the tool:

```
skill({ name: "git-release" })
```

## Configure permissions

Control which skills agents can access using pattern-based permissions in `opencode.json`:

```json
{
  "permission": {
    "skill": {
      "*": "allow",
      "pr-review": "allow",
      "internal-*": "deny",
      "experimental-*": "ask"
    }
  }
}
```

| Permission | Behavior                                  |
| ---------- | ----------------------------------------- |
| `allow`    | Skill loads immediately                   |
| `deny`     | Skill hidden from agent, access rejected  |
| `ask`      | User prompted for approval before loading |

Patterns support wildcards: `internal-*` matches `internal-docs`, `internal-tools`, etc.

---

## Override per agent

Give specific agents different permissions than the global defaults.

**For custom agents** (in agent frontmatter):

```yaml
---
permission:
  skill:
    "documents-*": "allow"
---
```

**For built-in agents** (in `opencode.json`):

```json
{
  "agent": {
    "plan": {
      "permission": {
        "skill": {
          "internal-*": "allow"
        }
      }
    }
  }
}
```

---

## Disable the skill tool

Completely disable skills for agents that shouldn't use them:

**For custom agents**:

```yaml
---
tools:
  skill: false
---
```

**For built-in agents**:

```json
{
  "agent": {
    "plan": {
      "tools": {
        "skill": false
      }
    }
  }
}
```

When disabled, the `<available_skills>` section is omitted entirely.

## Configure profile-based sources (V2)

On the V2 server, the `profile` block in `opencode.json` adds per-scope skill sources and rule bundles on top of the discovery locations above. This is useful for attaching a shared skill directory or inline rules to a specific session without changing global config.

```jsonc title="opencode.jsonc"
{
  "profile": {
    "skills": {
      "sources": [
        { "type": "directory", "path": "/abs/path/to/skills" },
        { "type": "url", "url": "https://example.test/skills/" }
      ],
      "selection": {
        "enable": ["review", "deploy-*"],
        "disable": ["experimental-*"]
      }
    }
  }
}
```

- `sources` — additional skill directories or URLs concatenated with the standard discovery sources.
- `selection.enable` — when non-empty, only skills whose `name` matches an entry are visible (wildcards `*` and `?` supported).
- `selection.disable` — matched skills are hidden. `disable` wins over `enable` when both match.

An empty or absent `profile` is the identity baseline: it adds nothing and removes nothing.

:::note
Profile-based sources require the OpenCode V2 server. On a V1 sidecar the `profile` block is parsed but ignored at runtime; check the server logs for a warning if you see it not taking effect.
:::

## Troubleshoot loading

If a skill does not show up:

1. For nested skills, verify `SKILL.md` is spelled in all caps; for flat skills, confirm the file has a `.md` extension
2. Check that frontmatter includes a valid `name` (or that the file/directory name supplies one)
3. Ensure skill names are unique across all locations
4. Check permissions—skills with `deny` are hidden from agents
5. On V1, confirm the `profile` block is not being relied upon—it is ignored outside V2
